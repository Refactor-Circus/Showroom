# Showroom

This repository is a Laravel package. Keep the package focused, idiomatic, and easy for Laravel developers to install, test, and maintain.

Showroom is a JSON API and MCP package: since v2.0.0 its PHP ships no UI (no Atrium plugin, views, Blade directives or screens). Front ends call the JSON API through the committed `openapi.json` and the TypeScript client in `client/`. Showroom does ship its Atrium front-end module, JS only: Vue sources in `atrium/` (pnpm, `@refactor-circus/atrium` SDK as a dev dependency, types from `client/src/schema.d.ts`), built into the committed `dist/atrium/` and declared in `composer.json` under `extra.atrium`, which Atrium v2 discovers and loads on its page.

## Package Conventions

- Use Laravel-native package APIs and the existing service provider shape before adding abstractions.
- Keep package names, namespaces, Composer metadata, publish tags, documentation, and examples aligned with `refactor-circus/showroom`.
- Add only the files and dependencies needed for the package behavior being implemented.
- Prefer explicit Laravel package code over helper abstractions unless the extension point is real.
- Keep tests focused on observable package behavior through public APIs, service provider wiring, commands, routes, published resources, and documentation promises.

## Architecture Conventions

- Code is organised into domain modules under `src/Domains/{Domain}` (namespace `RefactorCircus\Showroom\Domains\{Domain}`), mirroring the mono application's domain-module standard. Each domain has a `{Domain}ServiceProvider` (extending `RefactorCircus\Keystone\Support\ServiceProvider`), listed in `src/Domains/DomainServiceProvider.php`, its own API `routes.php` loaded through `loadApiRoutesFrom()`, and only the subdirectories it uses (`Models/ Policies/ Resources/ Enums/ Data/ Actions/ Events/ Http/{Controllers,Requests}/ Mcp/{Tools,Requests}/ Concerns/ Services/ Support/ Contracts/ Exceptions/ Console/`).
- Showroom stands on `refactor-circus/keystone`. `ShowroomServiceProvider` extends `RefactorCircus\Keystone\Support\PackageServiceProvider`: `definition()` describes the package (`Package::make('showroom', 'RefactorCircus\Showroom')`), `register()` calls `registerPackage()` right after merging config and before the domain providers, and `boot()` uses `registerPolicies()`, `registerNotFoundResponses()`, `registerMcpServer()`, `registerCortex()` and `loadHistoryRoutes()`. It keeps the rest of the cross-cutting wiring: translations, publish tags (`showroom-config`, `showroom-migrations`, `showroom-lang`) and the Impex integration.
- Use Keystone's classes rather than local copies: event contracts `RefactorCircus\Keystone\Contracts\{ActionStartingEvent,ActionFinishedEvent,ModelLifecycleEvent}`, the `RefactorCircus\Keystone\Models\Concerns\DispatchesModelEvents` trait, request bases `RefactorCircus\Keystone\Http\Requests\Request` and `RefactorCircus\Keystone\Mcp\Requests\Request`, `RefactorCircus\Keystone\Mcp\Tool`, `RefactorCircus\Keystone\Mcp\Server` (the base of `ShowroomServer`), `RefactorCircus\Keystone\Auth\Authorizer::for(...)` and `RefactorCircus\Keystone\Cortex\CortexIntegration::for(...)`. Catalog exceptions extend `RefactorCircus\Showroom\Exceptions\ShowroomException`, an abstract `PackageException` answering 409; the bundled policies extend `RefactorCircus\Showroom\Support\Policies\Policy`, which extends Keystone's `Policy`.
- Action input is a `final readonly` `{Action}Data` in the domain's `Data/` (on `RefactorCircus\Keystone\Data\Data`), never an array: fields are promoted constructor properties (camelCase of the input keys; enums for enum values; `T|Missing = new Missing` for partial updates, checked with `$data->has('x')`; dynamic maps such as product `values`, `associations` and labels stay `array` fields; a list of structured items is `#[ListOf(ItemData::class)] public array` of an item Data in the same `Data/` - `FamilyAttributeData`, `FamilyLevelData`, `Search\Data\Filter` - whose own `rules()` the parent prefixes (`Arr::prependKeysWith(ItemData::rules(), 'x.*.')`), and a nested Data such as `Search\Data\Complete` is built by Keystone from the parent's validated input, checked by its rules under `complete.` (`ListProductsData::completeRules()`)), `rules()` lives on the Data (with any context args), and the starting events that took input carry the Data. List Data expose `pagination()` (`Support\Paging::cursor()`, or `Paging::pages()` for product search, sized by `showroom.pagination`) and add its `rules()`; list tools take `+ ListXData::pagination()->schema($schema)`. HTTP and MCP requests validate once: their `rules()` return the identifier rules plus `XData::rules(...context)` (identifiers first), and `persist()`/`handle()` build with `XData::fromValidated($this->validated() / $validated)` - never `XData::from()` in a request (ArchTest). Code that vouches for its values uses `new XData(...)`. `tests/ArchTest.php` rejects array input on `execute()`, keeps every Data class in a `Data/` directory and everything there `final readonly`. Engine-internal values (`Search\Data\ProductQuery`, built by `ListProductsData::query()`, `SearchResults`, `Asset\Data\StoredFile`) stay plain `final readonly` classes. The Impex steps in `src/Impex` keep their array contracts (Impex stores and replays them) and build the Data inside.
- API resources extend `RefactorCircus\Keystone\Http\Resources\JsonResource` and declare `schema(JsonSchema $schema)` next to `toArray()` (always-present fields `required()`, conditional ones not, `nullable()`, enum values listed; ids are ULID strings). MCP requests answer with `(new XResource($m))->toStructuredResponse()` / `XResource::collection($page)->toStructuredResponse()` (lists carry their page under `meta`), and each tool declares `outputSchema()` as `XResource::structuredSchema($schema)` / `collectionSchema($schema, ListXData::pagination())` plus its extra keys, or a hand-written schema for plain answers (`{deleted, code}`). The transfer tools answer with Impex's `RunResource` the same way (`RunResource::structuredSchema($schema)`). `mcpTool()` in tests is Keystone's `Testing\McpTools::call()`, which checks every structured answer against the tool's schema, and `tests/Feature/Mcp/OutputSchemaTest.php` requires the declaration. `parityGaps()` uses `Testing\Parity` over the HTTP API and MCP (exceptions, each with its reason, in `PARITY_EXCEPTIONS` in `tests/Pest.php`: `ShowSettingsSummaryAction` has no MCP tool), and `tests/ArchTest.php` uses `Testing\Arch` over the domain Actions and the Impex steps in `src/Impex/Actions`: every Action dispatches a starting and a finished event (the steps' events live in `Domains\Transfer\Events`), writes inside `DB::transaction()` (starting event before it, finished event after it returns; jobs dispatched `->afterCommit()`), and every model fires a `{Entity}{Hook}Event` for every Eloquent hook (`Arch::modelEventGaps()`), `Search\Models\SearchableProductModel` included. Asset files are written before the transaction and removed with `DB::afterRollBack()` if it rolls back; files a change replaces or a delete drops go in `DB::afterCommit()`.
- History and auditing: Showroom audits only while Keystone's `Package::audits()` says so (refactor-circus/keen installed and `showroom.audit.enabled` on). Then the domain providers' `AuditHooks::label()` registrations run (inside `$this->app->booted()`), and `GET {showroom.routes.prefix}/history` (`showroom.history.index`) and `ListShowroomHistoryTool` (`list-showroom-history-tool`, in `ShowroomServer::TOOLS`) are offered; otherwise the route answers 404 and the tool is not offered. Never add audit tables or writers to Showroom. `tests/Keen` runs with Keen installed.
- The `Catalog` domain (`src/Domains/Catalog`, `RefactorCircus\Showroom\Domains\Catalog`) is read-only and owns no model: `GET {prefix}/stats` (`ShowCatalogStatsAction`, completeness cached for `showroom.stats.cache_seconds`, a constant query count pinned in `PerformanceTest`), `GET {prefix}/search` (`SearchCatalogAction`, the types filtered by `viewAny` through `Authorizer::for()`, 403 when none is allowed) and `GET {prefix}/settings-summary` (`ShowSettingsSummaryAction`, cast config, no MCP tool). It reads other domains' models and writes nothing; its Actions still dispatch a starting and a finished event and need no transaction. Put new cross-domain read views here, not in the domains they read.
- OpenAPI and the client: `openapi.json` and `client/` (`@refactor-circus/showroom-client`) are generated and committed. Run `composer client:generate` after changing a route, request rules, a Data's `rules()` or a resource, and commit both; `tests/OpenApi/OpenApiTest.php` (on `OpenApiTestCase`) fails while either is stale, without Node, and the `client` CI job regenerates and diffs. All Scramble configuration and extensions live in the workbench (`workbench/config/scramble.php`, `workbench/app/OpenApi/`); `src/` never names Scramble, which stays in `require-dev`.
- Missing records on Showroom's routes answer `{"message": "Not found."}` (`registerNotFoundResponses()`), guests get 401 and signed-in users without the ability 403.
- Eloquent models are `{Entity}Model` (`ProductModel` is a product, `ProductModelModel` a product model). Relations name their keys explicitly, because Eloquent guesses keys from class names.
- Models moved from `RefactorCircus\Showroom\Models`: each domain provider keeps the old class names (and the `showroom_*` aliases for products, product models and owners, listed first) as morph aliases through `keepMorphAliases()`. Model events map to `{Domain}\Events\{Entity}{Hook}Event`.
- Classes whose names are stored stay put: `src/Impex` (Impex stores flow, source and action classes) and `src/Jobs` (queued payloads).
- Everything Showroom sends out goes through Impex so it is recorded: feeds through `Impex::http()` or an Impex channel (`deliver_through`), vendor pushes through the product stream. The stream adapter lives in `src/Impex/Webhooks` (`ProductStream`, `ProductSnapshots`, `TopicMap`, `ProductScopeMatcher`, `ProductFormatter`, `CaptureProductChanges`) and is registered by `ImpexIntegration` only when `showroom.impex.webhooks.enabled` is true. `ProductSnapshots` loads a chunk of products in a constant number of queries; keep it that way. The topics in `showroom.impex.webhooks.topics` are stored as bits: append, never reorder.
- Tables: models resolve their table with `getTable()` from `Support\Tables` (`showroom.tables`, keyed by the name without `showroom_`); migrations, pivots, `Rule::unique`/`exists` (by model class), raw `DB::table()` queries, joins and qualified columns (`Tables::name('products').'.id'`) use the same keys, never literal `showroom_*` names (`tests/ArchTest.php` checks with `Arch::literalTableNames()`; explicitly named indexes keep their names). `tests/Modes/RenamedTables` reruns representative flows with every table renamed.
- Policies: every model has a policy in `showroom.policies` (`Arch::modelsWithoutPolicies()`), registered by `registerPolicies()`. Child records defer to their parent through `Support\Policies\Policy::defersTo()` (Keystone's `allowsOn()`): associations to their source, versions and completeness to their product; `SearchableProductPolicy` asks the product policy.
- Cross-domain code lives in `src/Support`.
- Batches cost a constant number of queries: product and product model lists eager-load what their resources read (`ListProductsAction::eagerLoads()`), export pages load `ExportProductPages::eagerLoads()` and published versions with `Versions::publishedSnapshots()`, search documents are built with `ProductDocument::many()`, and completeness refreshes in bulk; `tests/Feature/PerformanceTest.php` pins each with query counts. A write that reaches many products never lists them in its own transaction: it calls `ProductIndex::queueWithin(SyncScope, id)` (a queued `QueueProductSyncs` that walks them in chunks), and bulk writers wrap themselves in `ProductIndex::deferring()`. `SyncScope` values are stored in queued jobs: append, never rename.
- No UI and no Atrium in PHP: Showroom's PHP renders nothing and names no other package's UI. No file under `src/`, `config/`, `routes/`, `database/`, `lang/`, `resources/` (the Boost skill aside) or `workbench/` mentions Atrium, and `composer.json` names it only in `extra.atrium` (`tests/Feature/NoAtriumReferencesTest.php`); no `RefactorCircus\Showroom` class uses `RefactorCircus\Atrium` (`tests/ArchTest.php`), and Atrium is never required or suggested. Data a front end needs that the API lacks becomes an endpoint and MCP tool (usually in `Catalog`), never a view. History (Keen) and transfer runs (Impex) are read from those packages' own APIs. Domain providers register `AuditHooks::label()` only where the audit log's default naming falls short (localized labels, associations, versions).
- The Atrium module (`atrium/`): its Atrium integration (feature, nav items, widgets, settings panel, search source, screens) is declared in `atrium/src/integration.json`, a static JSON manifest (D-021); `composer.json`'s `extra.atrium.integration` names the built copy, `dist/atrium/integration.json`. A new screen, widget or nav item goes in that manifest and in the module entry, `atrium.ts` (`atrium/test/integration.test.ts` checks they match). After changing anything there, run `pnpm install`, `pnpm typecheck`, `pnpm test` and `pnpm build` in `atrium/` and commit `dist/atrium/` (with its `build.json`). `tests/Feature/AtriumModuleTest.php` fails, without Node, when the build is older than its sources, and the `ui` CI job rebuilds and diffs. `atrium/types/impex-schema.d.ts` is a copy of Impex's client schema for the transfers page (Showroom does not depend on Impex); refresh it by hand. After `composer client:generate`, typecheck the module too. Module components compose Nuxt UI (`UTable`, `USelect`, `UCheckbox`, `UButton`, `ULink`, ...) and the SDK's `Atrium*` components, never raw `<button>`, `<input>`, `<select>`, `<textarea>`, `<table>`, `<details>` or `<a href>`; `atrium/test/nuxt-ui-guard.test.ts` enforces it, and tests drive fields and rows through `atrium/test/ui.ts`.
- One config file, `config/showroom.php`. Existing keys are renamed or removed only in a major release, each listed in the CHANGELOG's upgrade note for that release (v2.0.0 removed `showroom.ui.*` and `showroom.atrium.*` and moved `widget_cache_seconds` to `showroom.stats.cache_seconds`); a new key is added under its own commented banner section.

## Quick Commands

- Full validation: `composer test`
- Formatting check: `composer lint:check`
- Static analysis: `composer analyse`
- Pest tests: `composer test:unit`
- Atrium module: `cd atrium && pnpm install && pnpm typecheck && pnpm test && pnpm build`, then commit `dist/atrium/`
- Regenerate `openapi.json` and `client/`: `composer client:generate` (needs Node); export the document only: `composer openapi:export`
- Workbench build: `composer build`
- Workbench server: `composer serve`
