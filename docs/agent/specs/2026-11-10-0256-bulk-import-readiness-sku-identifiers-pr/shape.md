# Bulk import readiness: SKU identifiers, product slugs, external IDs, batch upsert — Shaping Notes

## Scope

Changes to Showroom so a host app can load a large existing catalog (about 6.67M simple products under about 3.1k vendor and series owners) from a legacy database, re-run that load cheaply, and later keep it in step with an ERP (D365).

The first consumer is the `secret` app's chained Impex flow `core:catalog`:

- It first sets up the owner types, then runs `core:vendors`, `core:series` and `core:products` as child flows.
- That flow lives in the app and is not part of this spec.
- A later `d365:*` flow will find these records again by their ERP ids.

In scope:

1. **SKU identifiers.** A product `identifier` is the SKU and may hold any printable characters, up to 191 of them. Real SKUs contain spaces and `/`, for example `ML20906 HPSK 630 SEC M91 M92 LC LH` and `83AL-IC/40 4 RED ALUM`; about 5.8M of the 6.67M SKUs fail today's `^[A-Za-z0-9][A-Za-z0-9_.-]*$`. The pattern becomes configurable (`showroom.products.identifier_pattern`), and its default accepts real SKUs. The identifier is still unique and never changes.
2. **Product slugs.** A new `slug` on products: unique, never changes, and **always generated by Showroom** from the identifier (`Str::slug`, with a `-2`, `-3`, … suffix on collision). Callers cannot set it. The slug becomes the product route key on every product route (show, update, delete, versions, revert, transitions, assets, …), so a `/` or space in a SKU never reaches a URL. The API, MCP tools, search document and exports carry `slug`. Existing products are backfilled by a migration.
3. **External IDs.** A new `showroom_external_ids` table maps records to ids in other systems. A record can have any number of systems, for example `core`, `d365` and `uid`.
   - **Subjects:** products and owners only. Product models are not covered; they can be added when variant grouping arrives.
   - **Shape:** `subject_type`, `subject_id`, `system`, `external_id`. Unique on (`subject_type`, `system`, `external_id`), indexed on (`subject_type`, `subject_id`).
   - **Writing:** set through the create and update actions of products and owners (`external_ids: {system: id}`). On update, only the systems you send change, and `null` removes one.
   - **Reading:** returned by resources and MCP tools; filter or look up by `system` + `external_id`; carried in the product search document.
4. **Batch upsert.** A new batch action takes a list of product records and creates or updates them, matched by identifier or by an external id.
   - **Unchanged skip:** each record is first compared in memory with the stored product, as Roster's `preview()` does. An unchanged record writes nothing.
   - **Batched writes:** changed records are written in batches.
   - **Versions:** a new product gets one `created` version; an update records a version only when something changed.
   - **Other side effects:** unique values are synced, and indexing is queued once per batch rather than per product.
   - **Validation:** validation and ownership rules match `CreateProductAction` and `UpdateProductAction`. A failed record is reported with its reason and doesn't fail the rest of the batch.
   - **Impex:** `showroom:upsert-products` (and the file import, if it fits) moves onto the batch action, and host apps call the action directly from their own batch flows.
   - **Webhook opt-out:** callers can pass a flag that skips the product-webhook change capture (`CaptureProductChanges`) for initial loads. By default, changes are captured as usual.
5. **Owner type that is its own parent.** An owner type can list itself in `parent_types` when it's created (`vendor` under `vendor`, for umbrella companies). Today `CreateOwnerTypeData` validates `parent_types.*` with `Rule::exists`, so the type's own code is refused until it exists, and you have to create it and then update it. `allowsParent()` already handles a type parenting itself once the type is stored.

Out of scope (deferred):

- Owner values and metadata (logos, descriptions, flags).
- Stopping ERP-owned changes from demoting an `approved` product to `draft` (needed before the D365 flow).
- Configurable product statuses: the built-in four stay.
- External ids on product models.
- HTTP and MCP surfaces for the batch upsert.
- Any app-side flow.

## Decisions

- **Products vs models.** The import creates simple products only. Core has no variant grouping: each SKU stands alone with its vendor and series. Ownership (vendor → series → product) and variants (model → variant) are separate trees.
- **Slug is always generated.** The import does not carry the legacy core slug: 843 core slugs are shared by 1,686 in-scope items, because the core slug is derived from the SKU with punctuation collapsed. Storefront URLs may differ from core's.
- **Slug as route key.** Routes bind on the slug, not on the identifier. The identifier can still be used in inputs (`parent`, associations, filters) and stays the business key.
- **External ids are per system.** One row per (subject, system). Uniqueness is per system and subject type, so the same id can appear in two systems, and on an owner and a product.
- **Bulk surface:** an action plus an Impex flow. No new HTTP endpoint or MCP tool in this spec.
- **Webhooks during bulk loads:** captured by default, with an opt-out flag.
- **Statuses stay as they are** (`draft`, `in_review`, `approved`, `archived`). Imported products start as `draft`, and the importer sets `enabled`.
- **The consumer's data rules stay in the app:** skipping deleted, d1, redirected and duplicate-uid rows, and choosing series over vendor. Showroom stays generic.

## Context

### Consumer facts (core database, in import scope)

- Vendors: 1,715. 26 are umbrellas, each one level deep, with 41 children between them. **Umbrellas own series and products themselves**: Sargent has about 2M items.
- Series: 1,387. Series slugs change when a series is renamed, so the app uses `series-{core id}` as the owner code, and the `core` external id is the stable link.
- Products: about 6.67M d365 items. External ids are `core` (core id), `d365` (`source_id`) and `uid` (`profile_20`, absent on about 563k items).
- Owner types: `vendor` (can be a root, `parent_types: [vendor]`, owns products) and `series` (cannot be a root, `parent_types: [vendor]`).

### Product alignment

- Mission: "Dynamic hierarchical ownership", with `vendor → vendor → series → product` listed. Item 5 makes that chain possible to set up at create time.
- Roadmap item 7: "Import / export via Impex — bulk import/export built on Impex flows; syndication feeds and ERP/storefront connectors". This spec makes bulk ERP-scale loads practical.
- Mission: "Full HTTP API with MCP parity". External ids and slugs appear on both surfaces. The batch action is deliberately action- and flow-only for now.

## Standards

- `actions/actions-events`: new batch action and changed create/update actions; event pairs, transactions.
- `data/data-objects`: new batch Data object; `external_ids` added to the product and owner Data; identifier rules.
- `models/models`: external-id model, `slug` on `ProductModel`, configurable table name.
- `models/migrations`: new table, slug column with backfill, sequence filenames.
- `models/stored-identifiers`: slug as the record reference in routes; inputs keep referencing by identifier or code; external ids.
- `architecture/configuration`: `showroom.products.identifier_pattern`, the batch size, `showroom.tables.external_ids`.
- `architecture/dependencies`: the batch flow sits in the optional Impex integration; the core batch action must not import Impex.
- `http/resources`: `slug` and `external_ids` on product and owner resources.
- `http/routes`: slug binding on product routes.
- `http/request-persist`: product and owner requests take `external_ids`; route-model lookup by slug.
- `http/authorization`: the batch action authorizes each record as create/update would; external ids follow their subject's policy.
- `testing/test-layers`: behaviour tested at the action; surfaces test their wiring only.
- `testing/arch-tests`: new action, Data and model must pass the arch preset.
